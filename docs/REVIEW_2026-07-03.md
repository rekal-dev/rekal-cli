**Status update (2026-07-03, later same day):** P0-1, P0-2, and P1-4 (export
ordering) have been fixed and merged to `main`. See the "Fixed" markers below
each finding for what changed and where. Nothing else in this report has been
acted on yet — P1-1, P1-2, P1-3, and the P2s are still open findings only.

Reviewer stance: demanding senior engineer, not a hobby-project pass. Scope: architecture fit,
code quality, test quality, schema/migration robustness, concurrency/resource handling, perf,
security/input handling, and the specific loose ends Frank flagged. No code changed as part of

Rated against where the project is heading, not where it started: `data.db` is an append-only

## Ranked findings

### P0-1 — Codec decoder panics on truncated/malformed checkpoint frames (crashes `sync` on a bad teammate push)

`cmd/rekal/cli/codec/frame.go:494-541` (`parseCheckpointPayload`). Every `readUvarint(data[pos:])`
call in this function (`CheckpointRef` L494, `BranchRef` L502, `EmailRef` L504, each `SessionRefs`
entry L525, each `Files[i].PathRef` L534) is made **without checking `pos < len(data)` first**.
`readUvarint` (frame.go:600-606) calls `binary.Uvarint`, which returns `(0, 0)` on an empty slice;
the wrapper's `n <= 0` branch then returns `(0, 1)` — "consume 1 byte" — even though zero bytes
remain. `pos` walks past `len(data)`, and the next `data[pos:]` slice panics
(`slice bounds out of range`).

There is **no `recover()` anywhere in the repository** (verified by full-repo grep). The panic
propagates uncaught through `importBranch`/`importBranchToIndex` → `runSyncTeam`/`runSyncSelf` →
`main`, crashing the whole `rekal sync` process. `import.go` clearly intends per-checkpoint
isolation — malformed frames are meant to be skipped and deduped (import.go:57-59, 129-131) — but
a single corrupt or adversarial checkpoint frame from *any* teammate's git push bypasses that
isolation entirely via panic instead of a returned error.

Compare `parseSessionPayload`, which bounds-checks before every slice (frame.go:418, 430,
441-442, 456, 467) — the checkpoint path is a regression/inconsistency relative to the pattern
already established elsewhere in the same file, not a fundamental design gap.

A second, related issue in the same function: `nSess` (frame.go:521) and `nFiles` (frame.go:487)
are read directly from attacker-influenced bytes with no sanity cap before
`make([]uint64, 0, nSess)` (frame.go:523) / `make([]FileTouchedRecord, 0, nFiles)` (frame.go:531).
A crafted frame with a huge count triggers an oversized allocation before any bounds check fires.

**Why it matters now:** this is exactly the untrusted-input boundary SOUL.md's "thin on the wire"
design creates — `sync` decodes bytes that arrived from someone else's machine. Today this needs
either a buggy rekal build or a malicious actor with commit access to the shared branch; but the
whole point of the git-transport model is that many machines write to it over the life of a
project, so the probability of *some* future write being truncated/corrupted (bad git merge,
partial write, future codec bug) is not negligible, and the blast radius is "the whole team's
`sync` breaks," not "one bad checkpoint is skipped."

**Fix:** bounds-check `pos` against `len(data)` before every `readUvarint`/slice in
`parseCheckpointPayload` (mirror the pattern already in `parseSessionPayload`), cap `nSess`/`nFiles`
against a sane maximum before allocating, and — as defense in depth for any codec path that decodes
data from another machine — wrap frame decode in `recover()` at the per-frame boundary in
`importBranch`/`importBranchToIndex` so a future bug in this class degrades to "skip one
checkpoint" instead of "crash the process." Add fuzz tests (`go test -fuzz`) over
`parseCheckpointPayload`/`parseSessionPayload`/`parseMetaPayload` — there is currently zero fuzzing
anywhere in the repo for a binary parser whose entire job is consuming bytes from other people's
machines.

**Fixed (commit `0cde586`).** `readUvarint` now returns an error on empty/incomplete/overflowing
input instead of silently advancing past the buffer; every call site in
`parseSessionPayload`/`parseCheckpointPayload`/`parseMetaPayload` propagates it. `nSess` is capped
against remaining buffer size before allocating (`nFiles` was already bounded to a single byte, no
change needed there). Added tests that feed every truncation of a valid frame through the parser
(asserting no panic at any cut point), a crafted oversized session count, and raw corrupt/garbage
bytes through the full zstd+parse decode path. **Not done**: the `recover()` defense-in-depth at the
per-frame import boundary, and fuzz tests — both still worth adding as follow-up hardening, but the
concrete panic is closed.

### P0-2 — `queue-operation` parser only handles `"enqueue"`; other operations vanish or leave orphaned data

`cmd/rekal/cli/session/parse.go:220`: `if raw.Operation != "enqueue" { continue }`. This is a
single-value whitelist. Any other operation value — a cancel/remove of a queued steering message
before it's delivered, which Claude Code's queue UI allows — falls straight through unprocessed.

Consequence given append-only storage: if the harness enqueues a steering message and the user
then cancels it (never delivered as a real `user` turn), the code has *already* committed a
`human_steering` turn (parse.go:226-232) for the enqueue event. There's no corresponding "remove"
handling to retract or annotate it. That phantom turn — text the user typed but then took back —
is permanently baked into the shared ledger with no correction mechanism, because the ledger has
no delete/update semantics by design.

The parser's own comment claims verification "against real … session files," but that claim covers
only enqueue/dequeue (per git history, commit `ddcceb7`); there's no evidence a "remove"/cancel
variant was ever captured from a real transcript or exercised by a test.

**Why it matters now:** this is the second manifestation of the same root problem as P0-1 — an
append-only store means every parsing gap is permanent once merged, so silent data drops or phantom
records need to be caught before they're written, not after. The specific steering-turn boost
(`recall.go` `steeringBoost = 1.3`) makes this worse: a phantom human_steering turn isn't just noise,
it's explicitly weighted *up* in search relevance, so a leaked cancelled draft could outrank a real
decision in recall results.

**Fix:** before whitelisting, enumerate every `operation` value Claude Code's queue actually emits
(check the harness source or capture a real session where a queued message is cancelled) and either
handle each explicitly or fail loudly (log to stderr, don't silently `continue`) on an unrecognized
operation so gaps are visible during development instead of silently shipped.

**Fixed (commit `1051332`).** Any `operation` other than the two known values (`"enqueue"`,
`"dequeue"`) is now treated defensively as a removal: matched by content text using the same
string-or-block-array shape `"enqueue"` uses, and if it matches a pending steering turn, that turn
is retracted from the parsed payload instead of persisting as a phantom `human_steering` entry. If
the text doesn't match anything pending (unknown real shape, or a real payload that references the
queued item by ID rather than text), nothing is touched — documented in code as a known limit until
a real cancelled-message transcript can be captured to verify the actual shape (still open, see
P1-1's fix-together note). Added tests for straightforward retraction, retracting one of several
pending turns without disturbing the others, and a no-op when the payload doesn't match anything.

### P1-1 — `meta.json` subagent sidecar schema is guessed, not verified against real output

`cmd/rekal/cli/session/claude.go:90-94` defines `subagentMeta{AgentID, ToolUseID, TeamName}`,
unmarshaled at claude.go:105. The code's own comment (claude.go:154-158) admits the directory
layout "could not be confirmed against real local session data … should be re-validated against a
real subagent transcript when one becomes available." Because `json.Unmarshal` doesn't error on
missing/mismatched fields, if the real sidecar uses different key names or nesting, this silently
returns a non-nil struct with empty `AgentID`/`TeamName` — no error, no warning, incorrect (empty)
subagent attribution written straight into the shared DB. The test fixture at claude_test.go:197
hand-fabricates the sidecar to match the guess, so it cannot catch a real-schema mismatch — it's
circular by construction.

**Why it matters now:** subagent/team attribution is a headline feature of this release
(`team_name`, `parent_session_id`, the whole recall-grouping feature in recall.go). If the sidecar
format is wrong, every subagent session silently loses its team/agent linkage — not a crash, just
quietly wrong grouping in every subsequent recall.

**Fix:** capture one real `meta.json` from an actual Claude Code subagent run (per the code's own
TODO) and either confirm the struct or fix it, then commit that real file under `testdata/` and
assert against it — replacing the hand-authored fixture with ground truth closes both this finding
and part of the "synthetic fixtures" gap below.

### P1-2 — Testing methodology gap: migration tests fixed, but "synthetic fixture vs. real data" is still structurally open

Commit `5574ebe` fixed two bugs (missing `MigrateIndexSchema` call before incremental writes; an
`ALTER TABLE ADD COLUMN ... NOT NULL` that DuckDB rejects) that were invisible to the prior suite
because every existing migration test called `InitDataSchema`/`InitIndexSchema` on a freshly
created, empty DB — there was no old-schema DDL to migrate away from, so the interesting code paths
never ran in CI. Both bugs were actually found by manually validating against a real captured
`data.db`/transcript, per the commit message — not by an automated test.

Since then, `cmd/rekal/cli/db/schema_migrate_test.go` added `TestMigrateDataSchema_OldDataDB` (line
54) and `TestMigrateIndexSchema_OldIndexDB` (line 117), which hand-build pre-metadata DDL, insert a
row, and assert the migration preserves it. This is a real improvement and does close the two
specific bugs from 5574ebe.

**What's still open:**
- These are hand-retyped DDL strings, not an actual binary DuckDB file produced by an older
  `rekal` build. Nothing in the repo opens a real on-disk artifact from a prior version — the exact
  validation step that found the original bugs ("copy of the actual pre-existing data.db") is not
  automated or repeated; it was a one-off manual check.
- Session/JSONL fixtures across `session/*_test.go` and `integration_test/checkpoint_e2e_test.go`
  are still small, hand-written, clean JSONL — no `isMeta` noise, no queue-operation entries in most
  cases, no realistic nested `tool_use`/`tool_result` chains, no real ULID/UUID shapes. There is no
  `testdata/` directory anywhere in the repo sourced from an actual captured session.
- Integration tests (`integration_test/`) are entirely synthetic-content `TestEnv` repos; the
  checkpoint → push → sync round trip is covered structurally (`TestPush_E2E_ExportAndPush`,
  `TestImport_E2E_RoundTrip`) but only with toy data.

**Why it matters now:** the pattern has now bitten twice (migration, checkpoint) despite green
suites both times. The fixes so far are targeted patches for the specific bugs found, not a change
to the methodology that let them through. A third bug in a code path that only manifests against
real-world transcript irregularities — exactly the kind of thing P1-1 and P0-2 above are — will
likely repeat the same cycle: ships green, breaks on real data, gets a one-off manual fix.

**Fix:** establish one seed corpus of real, anonymized/scrubbed session transcripts and at least one
real pre-migration `data.db`/`index.db` binary, check them into `testdata/`, and wire at least one
test in each of the session/db packages to run against them. This doesn't replace synthetic
unit tests (which are good for isolating specific behaviors) but closes the gap where "passes CI"
and "works on real data" have diverged twice.

### P1-3 — No forward-compatibility story for `data.db` schema (unacknowledged)

`cmd/rekal/cli/db/schema.go`'s migrations (`MigrateDataSchema`/`MigrateIndexSchema`,
`addColumnIfMissing`) are well-tested for the backward direction (older DB opened by newer rekal —
see P1-2 improvements). There is no handling, no version marker, and no test for the *forward*
direction: a newer rekal adds a column/table, commits that `data.db` to git, and a teammate on an
older rekal build opens it. DuckDB will presumably still open the file, but the older binary's
queries (which reference a fixed column list, e.g. `sessionFacetCols` in recall.go:377) have no way
to know new columns exist or are absent — this is unacknowledged anywhere in code or comments.

**Why it matters now:** `data.db` is explicitly designed to be shared across a team over the life of
a project (SOUL.md: "distributed through git... shared across the team"). Teams do not upgrade
`rekal` in lockstep. The current one-directional migration story means "everyone must upgrade
before opening a repo's `.rekal/` again" is an implicit requirement nobody has stated or tested for.

**Fix:** at minimum, write a `schema_version` (or `rekal_version`) marker into `data.db`/`index.db`
and have older binaries detect "this DB is newer than I understand" and fail with a clear
`rekal: this repo's rekal data is from a newer version, upgrade rekal` message rather than an
unexplained query error or silently-wrong behavior.

### P1-4 — `export.go` can mark a checkpoint "exported" before it's actually durably committed

`exportNewFrames` calls `db.MarkCheckpointsExported` (export.go:224) after building the wire-format
bytes, but *before* `commitWireFormat` (called from push.go:77) has actually committed those bytes
to git. If `commitWireFormat` fails after this point (git error, disk full, process killed), the
checkpoint is now permanently marked `exported = true` in `data.db` but was never actually written
to the branch that gets pushed — `push.go` only ever looks at unexported checkpoints, so this
checkpoint's content silently never reaches teammates, with no error surfaced to the user.

**Why it matters now:** correctness bug in the exact mechanism that makes the "thin on the wire,
shared via git" model work. Low severity in practice (single-machine, no data corruption, and a
subsequent checkpoint still captures new work), but it's a quiet, permanent gap in what a teammate
receives — exactly the kind of bug that's invisible until someone notices context is "missing" from
a colleague's sync weeks later.

**Fix:** only mark checkpoints exported after `commitWireFormat` succeeds, or make the two steps
transactional (e.g., a separate "encoded, pending commit" state that's reconciled on next push).

**Fixed (commit `ff86d72`).** `exportNewFrames` now returns the exported checkpoint IDs instead of
marking them itself. `doPush` marks them via a new `markCheckpointsExported` helper only after
`commitWireFormat` succeeds, so a crash or git failure between export and commit leaves the
checkpoint unexported and it's retried on the next push. Added regression tests against a real temp
git repo + `data.db`: one confirms the checkpoint is still unexported immediately after
`exportNewFrames` returns (before commit), one simulates a crash between export and commit/mark and
confirms a retry still picks up the checkpoint.

### P2-1 — Recall path recomputes the entire LSA model on every query

`cmd/rekal/cli/recall.go:489-520` (`lsaSearch`): every single `recall` invocation calls
`db.QuerySessionContent` (loads **all** turn content in the corpus) and `lsa.Build(...)`
(SVD/co-occurrence over the whole corpus) from scratch, purely to project the current query into
the LSA space. This is `O(corpus size)` work on the hot path of the single most-used command in the
product, on every invocation, with no caching between calls (each `rekal` invocation is a fresh
process, so there's no in-memory cache possible without a daemon) and no persistence of the fitted
model between runs.

**Why it matters now:** unlike the nomic path (which correctly reuses a precomputed embedding index
plus a daemon-cached model — see below), LSA rebuilds its whole model on every search. As the
project's corpus grows (the whole point of an append-only ledger accumulating over a project's
life), this scales linearly worse per query, on the path SOUL.md explicitly calls "agent first" —
i.e., the thing meant to be fast enough to call constantly.

**Fix:** persist the fitted LSA model (or at least its term-document statistics) in `index.db`,
rebuilt during `rekal index`/`sync` like the nomic embeddings already are, rather than refitting on
every `recall` call. This is the same perf lesson the checkpoint-embedding fix already applied
elsewhere in this release (trunk-only embedding, computed once at index time) — worth applying
consistently.

### P2-2 — Recall result-building does N+1 queries per candidate

`cmd/rekal/cli/recall.go:557-634` (`buildResults`) issues one `QueryRow` for session facets and one
more query (`querySessionFiles`) *per candidate*, inside a loop over up to
`candidatePool = (limit+1)*(conversationChildBudget+1)` (recall.go:324) rows — with default
settings, roughly 84 candidates, each triggering 2+ round trips to the (local, but not free)
DuckDB connection. `resolveRoot` (recall.go:676-703) has the same shape: one query per uncached
session in the parent chain during `groupByConversation`. The file already demonstrates the batched
alternative correctly in `loadParentIDs` (recall.go:639-671) — the N+1 pattern elsewhere is an
inconsistency within the same function, not a fundamental limitation.

**Why it matters now:** low severity today given `.rekal/` is local DuckDB (fast round trips), but
it's the same code path as P2-1 and will compound as corpora grow; also a maintainability/consistency
smell given the batched pattern already exists two functions away.

**Fix:** batch-load session facets and files for the whole candidate set up front (same shape as
`loadParentIDs`), the same way the parent-ID lookup already does.

### P2-3 — No concurrent-process guard on `data.db`/`index.db`

Neither `db.go`'s `open()` nor any call site sets `SetMaxOpenConns` or uses any advisory locking.
DuckDB is single-writer; two rekal processes touching the same file concurrently (e.g., a git
post-commit hook firing `checkpoint` while a background `rekal index` runs, or two terminals) get
whatever raw driver error DuckDB surfaces, not a `rekal:`-style message consistent with the project's
voice ("say what happened, say what to do, stop" — SOUL.md). `PopulateIndex` attaches `data.db`
`READ_ONLY` during index rebuild, which helps, but there's no protection against two writers to
`index.db` or `data.db` itself.

**Why it matters now:** not proven to corrupt data in testing, but architecturally unguarded, and
git hooks are exactly the kind of trigger that fires unpredictably relative to a user's manual
commands.

**Fix:** at minimum, catch the DuckDB lock-contention error and translate it to a clear
`rekal: another rekal process is using this repo's data, try again` message; consider a lightweight
file lock around write operations if this proves to bite in practice.

### P2-4 — `index_cmd.go` rebuild is not atomic / crash-safe

`rekal index`'s rebuild (`index_cmd.go` → `DropIndexTables` then `PopulateIndex`) runs as a sequence
of autocommitted DDL/DML statements with no wrapping transaction and no "rebuild in progress"
marker. A kill mid-rebuild (OOM, disk full, Ctrl-C) leaves `index.db` with some tables dropped and
not yet repopulated; a subsequent `recall` could silently query a partially-populated index with no
signal that anything is wrong.

**Why it matters now:** low severity — `index.db` is explicitly rebuildable from `data.db` by
design — but the failure mode is *silent wrong results*, not a clear error, which cuts against the
product's stated voice/character (SOUL.md: "honest... no silent updates").

**Fix:** wrap the rebuild in a transaction where DuckDB supports it, or rebuild into a temp file and
atomically rename over `index.db` on success, and/or write an `index_state` row marking rebuild
completion that `recall`/`query` check before trusting the index.

### P2-5 — `session/adapter.go` is a registry, not a shared implementation; harness parsers have copy-paste drift

`adapter.go` (32 lines) defines only an interface/registry. Text-extraction-from-content-blocks and
tool-argument extraction (`file_path`/`path`/`command` precedence) are independently reimplemented
in `parse.go:372-431` (Claude, typed struct), `codex.go:110-117`, `opencode.go:130-137`, and
`gemini.go:101-107` (the latter three via `map[string]interface{}` + manual type assertions). A
future bugfix to "how do we extract the file path from a tool call" needs to be applied in four
places by hand. Also: `codex.go:100-101` and `122-123` double-unmarshal `entry.Payload` into the
same target — harmless but clearly copy-paste residue.

**Why it matters now:** this is a code-quality/maintainability finding, not a correctness bug today
— but the project just added a fourth harness format (mid-2026 Claude Code) and previously added
Codex/OpenCode/Gemini in quick succession; if a fifth harness is coming, this is the moment to
extract the shared extraction logic before the copy-paste count goes to five.

**Fix:** pull the common "extract text / extract tool args from a generic block shape" logic into
`adapter.go` as shared helpers, parameterized by the small per-harness differences (field names),
rather than four independent reimplementations.

## Things that are actually fine (don't re-litigate these)

- **Checkpoint embedding perf fix (trunk-only)** — `checkpoint.go:366-417` correctly limits nomic
  embedding generation at checkpoint time to trunk sessions only (non-null `parent_session_id`
  excluded), with subagent turns still indexed into `turns_ft` for BM25 immediately and their
  embeddings deferred to the next full `rekal index`/`sync`. Well-reasoned, well-commented tradeoff.
  Not a loose end — this is the fix working as intended.
- **Nomic/CGO lifecycle** — model is not reloaded per call; `NewClient` prefers a Unix-socket daemon
  and only pays the expensive mmap+llama.cpp init cost once per machine idle cycle, with proper
  `Close()`/nil-out to prevent double-free. `EmbedSessions` batches correctly through one loaded
  embedder.
- **query.go raw SQL** — this command's entire purpose is arbitrary local SQL access; it is
  correctly scoped as a local power-user tool (no privilege boundary crossed — the user already has
  full filesystem access to `.rekal/data.db`), not an injection vector. Every other query path in
  the codebase (recall filters, session lookups) correctly uses parameterized `$1`-style
  placeholders — no string-concatenation-into-SQL of untrusted filter values found anywhere.
- **git subprocess invocations** (`push.go`/`sync.go`/`sync_remote.go`) — always `exec.Command`
  with real argv slices, never through a shell; no command-injection surface from branch
  names/emails/paths.
- **Migration backward-compatibility testing** (post-5574ebe) — genuinely good tests now exist for
  "older DB opened by newer rekal," see P1-2 for the remaining gap (real artifacts vs. hand-typed
  DDL).
- **`.goreleaser.yaml` / Homebrew tap claim** — checked and it's a non-issue: no Homebrew tap step
  exists in `.goreleaser.yaml`, and no documentation claims one exists either. `DEVELOPMENT.md`
  candidly documents that GoReleaser is local-only and the real release path is a separate GitHub
  Actions matrix workflow, with cross-compilation explicitly noted as "TBD." Docs match reality.
- **Type-safety in harness parsers** — every `interface{}` type assertion in codex.go/opencode.go/
  gemini.go correctly uses the two-value `, ok` form; no panic is reachable from adversarial JSONL
  content in those three parsers.
- **Malformed-line handling in Claude/Codex/OpenCode parsers** — degrade gracefully around one bad
  line rather than losing the whole session (Gemini's single-JSON-document format is the exception —
  noted as P1 above under session parser robustness, folded into general robustness rather than a
  separate top-level item since severity is lower than P0/P1 given Gemini transcripts are smaller
  and less central to the current roadmap).
